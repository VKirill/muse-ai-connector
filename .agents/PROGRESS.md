# Muse AI connector (bb-plugin-muse) — progress

## Now
- Node bridge `musebridge` (playwright-core, persistent Chrome profile per account) drives muse.ai: `doctor`, `chats`, `history`, `send`, `login`, `approve`, `accounts list|add|check|refresh|remove|set`; reads the page's IndexedDB `hatch-chat-cache` (transcript + chat-list parsers, hard `schemaVersion 4` check). Account pool: `accounts.json` registry, per-account slot locks (slot 0 is the classic `locks/<id>.lock` so default one-chat behaviour is unchanged, extra slots `locks/<id>.<n>.lock`, stale after 30 min or dead pid, `account_locked` only when all slots are busy), `pickAccount()` prefers the signed-in account with the fewest busy slots (ties: least-recently-used); slots are opt-in via `maxParallel` (accounts.json) / `MUSE_MAX_PARALLEL` / default 1, cap 50 (`accounts set <id> --max-parallel N`, `accounts list` shows `busy/max`), so one account can serve several chats at once; `accounts add` opens a headed Chrome sign-in window. Chrome launches force `en-US` and the composer is matched by a language-independent selector (`COMPOSER_SELECTOR`, `BUSY_TEXTS`), so any profile language works. All state files (`accounts.json`, `sessions.json`, `cookies.json`) are written atomically (same-dir temp file + rename, parse-error-tolerant reads) with a cross-process read-modify-write lock (`bridge/json-file.mjs`), so parallel Muse processes never crash on — or wipe each other's — half-written state.
- `muse-acp` ACP agent over stdio: a BB session pins one account + Muse side chat (`sessions.json`), streams `agent_message_chunk`s back; Muse hears only the user's words (`bridge/acp-prompt.mjs` strips BB `<system_instructions>`/`<system-reminder>` blocks; empty after stripping → short note, no Chrome launch) while `extractBbContext` keeps the project instructions, the owner-taught rules and the `# Language` section from BB's system block and prepends them to the prompt when they change (plugin manuals, skills catalogues and memory indexes dropped, 16 KB cap) — Muse follows the project's and the owner's rules without BB's whole system block; the Muse chat id is saved as soon as the URL carries it, and an interrupted turn's pending reply is polled until it finishes (`bridge/acp-pending.mjs`, `MUSE_PENDING_WAIT_MS`) and flushed to BB before the next prompt — one Muse chat per BB thread; several BB sessions can share one account concurrently when its slots allow — each session acquires its own slot and the sessions share the per-account API client; advertises model `muse-spark` (`session/new` models block, `session/set_model` accepted) and accepts BB reasoning levels `none–high` (Muse ignores the knob); `MUSE_BRIDGE_FAKE=1` swaps in a fake driver for tests. Muse works as a full local agent: the first message of a chat carries an intro that says the workspace is on the user's machine and reachable only through muse-tool blocks (Muse's own cloud-VM shell/tools must not touch it; first step `list_dir`), and the last `muse-tool` fenced block of Muse's reply runs a local tool — read_file/write_file/edit_file/list_dir/grep/bash inside the session cwd (paths outside refused, outputs capped; file I/O goes through the ACP client's fs/* requests when the client announced them) — with the text before the block streaming as `agent_thought_chunk` plus `tool_call`/`tool_call_update` updates and at most `MUSE_MAX_TOOL_ROUNDS` (default 60) rounds; a reply with neither a muse-tool block nor the final `[[done]]` line (requested in the intro, stripped before streaming) no longer ends the turn with the task undone — Muse gets a nudge to send the block or repeat its answer with `[[done]]` (the 2nd block-less reply in a row becomes the final answer); the session's MCP servers from `session/new` (stdio and http, a failing server skipped) attach as `mcp__<server>__<tool>` tools with `tool_schema`, and skills are reachable via `list_skills`/`read_skill` (`MUSE_SKILL_DIRS` or the default .claude/.agents skill dirs in cwd and home plus `~/.bb/skills`). Approval cards in a chat the connector drives are answered «Always allow» at once (`bridge/permissions.mjs`, never clicks Deny); money cards are left to the owner with a one-line «Muse asks for approval» notice, `musebridge approve --chat <id>` answers pending cards in an existing chat, and long agentic replies are covered by `send --timeout` plus the DeepSWE relay timeout `MUSE_RELAY_REPLY_TIMEOUT_SEC` (default 5400 s).
- Direct Muse API client is the default transport: each account's cookies live at `~/.muse-bridge/accounts/<id>/cookies.json` (mode 0600; `accounts refresh <id>` re-exports them from the signed-in profile), `bridge/protocol/gateway.mjs` bootstraps the way the web app does — it reads authToken/gatewayUrl/vmId from the muse.ai page's Next.js flight data (`parseBootstrapFromHtml`, `/api/hatch/token` only as a fallback), sends browser headers on every `/api` call, dials `wss://hatch.metaaivm.com/v1/noise` over HTTP/1.1 with the `ws` package (Origin + Chrome-UA headers; Node's undici `WebSocket` negotiates HTTP/2 via ALPN and the gateway closes with 1006), then vm wake + Noise XX — bodies and streams are sniffed for the zstd magic so responses without a `content-encoding` header decode (`bridge/protocol/ndjson.mjs`), and the live probe got through dial + handshake to a real `GET /api/session/list` body — and `bridge/protocol/api.mjs` speaks chats (send → deltas → final message, same shape as the browser `send`); a reply that outlives one WebSocket keeps going — `send()` resubscribes to `/chat/subscribe` with the last seen `stream_seq`/`chat_event_seq` (backoff 1/2/5 s… capped 30 s, no duplicate deltas) and `connectGateway` reconnects once per call, ending the `Muse gateway socket closed` losses on minutes-long replies. The gateway context in the flight data is located by content (`"authToken"`/`"cvmMigrationInventorySnapshot"`), not by the unstable `ef:` row label, so the real muse.ai page parses. `musebridge`/`muse-acp` pick `--transport api|browser` — api is the default, missing cookies or 401/403 fall back to Chrome, `MUSE_TRANSPORT=browser` forces it; Chrome is now only for sign-in and fallback.
- BB plugin "Muse" registered (provider id `muse`; package `bb-plugin-muse` 0.1.1, ESM, Node 22; settings `agentCommand`, `headless`, `replyTimeoutSec` passed as env): settings screen in BB Settings → Plugins → Muse manages accounts per host (add/check/remove, busy pill), EN+RU i18n, Pokecut styles; README EN + «По-русски».
- DeepSWE v1.1 pilot kit under `bench/deepswe/` (repo only, not installed on ovh-main): sudo-gated sandbox scripts (`server/setup.sh`, forced-command shell, docker-exec), Pier agent `muse_agent.py` on Pier's own `pier.agents.base.BaseAgent`, `run-pilot.sh` works over plain ssh (`$HOME/.local/bin` prepended to PATH — a non-login ssh lost `pier` — and `--n-concurrent "${CONCURRENCY:-1}"`: one trial at a time, the sandbox serves only the current container), Mac relay `relay.mjs` survives a failed round (busy/locked account or ssh hiccup logged as `round_error`, the queue item retries on the next poll, exits only on `--once`), `report.mjs` pass@1 summary.
